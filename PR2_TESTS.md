## Что покрыто

- **Платежи (деньги)** — `test_payments.py`: верификация подписи **Click**
  (валидная проходит; подменённая сумма/сервис — отклоняются; без секрета —
  fail-closed), авторизация колбэка **Payme** (Basic `Paycom:<ключ>`; неверный
  ключ/логин/без заголовка — отказ), конверсия суммы в тийины и сверка суммы.
  Это ровно те функции, поломка которых = пропущенный или поддельный платёж.
- **Вход в приложение (безопасность)** — `test_auth_otp.py`: хэш OTP
  детерминирован, зависит от `SECRET_KEY`, нормализация телефона.
- **Базовая целостность** — `test_smoke.py`: `manage.py check` проходит; факт
  создания тест-БД = **все миграции накатываются** (ломаная миграция завалит
  весь прогон); ORM жив (CRUD по `Country`).

Все утверждения в `test_payments.py` проверены на реальном коде `click.py` /
`payme.py` из репозитория.

## Как гонять локально

Тестам нужен рабочий `SECRET_KEY`. Проще всего — `DEBUG=True` (тогда в
`settings.py` подставляется dev-ключ). В корне проекта в `.env` уже должен быть
`DJANGO_DEBUG=True`; если нет — добавь, либо задай переменные в команде:

```bash
# внутри активированного venv
python manage.py test foodcost -v2
```

Ожидаемо: все тесты зелёные. Если упадёт — пришли вывод, разберём (частая
причина локально: не удалён старый `foodcost/tests.py`, либо нет `.env` с
`DJANGO_DEBUG=True`).

## CI (GitHub Actions)

`.github/workflows/ci.yml` на каждый `push` и PR: поднимает Postgres, ставит
зависимости, гоняет `check` + `migrate` + `test`. Так ломаную миграцию или
упавший тест видно **до** деплоя. Значения `DJANGO_*` в CI — тестовые, не боевые.
