# PR #3 — Фундамент мультиарендности (план)

Цель: безопасно довести изоляцию до продуктового уровня. Делаем маленькими
шагами, каждый — под тестом. Хорошая новость из аудита: изоляция на входе уже
централизована в `foodcost/views.py` (`get_country(slug, user)` → чужой
арендатор = 404). Значит мы не строим с нуля, а укрепляем и закрываем дыры.

## Терминология
`Country` в коде фактически = «арендатор» (tenant). Переименование
`Country→Tenant` — косметика, которая затрагивает 42 FK и 243 ссылки, поэтому
делаем её **последней**. Сначала — функциональная безопасность.

## Шаги

### 3.1 — Тест-ловушка на изоляцию ✅ (этот шаг)
Файл: `foodcost/tests/test_tenant_isolation.py`.
Закрепляет контракт: пользователь арендатора A не видит данные B; `get_country`
даёт 404 на чужой слаг; скоуп-выборка не протекает. **Ожидание: тесты проходят
уже сейчас** — это guardrail на время остальных шагов.
Прогон: `python manage.py test foodcost.tests.test_tenant_isolation -v2`.

### 3.2 — Аудит точек входа (где изоляция может протекать)
Найти вьюхи, которые принимают `country_slug`, но:
- резолвят `Country` **не** через `get_country(slug, user)` (значит не проверяют
  доступ пользователя), или
- делают запрос без `.filter(country=...)`, или
- дёргают дочернюю модель напрямую (`OrderItem/PaymeTransaction/StockMovement`
  и т.п.) мимо родителя.
Результат — список файлов/строк на починку. (Готовлю отдельно.)

### 3.3 — Убрать фолбэк `get_public_country()` на «uzbek»
Файл: `foodcost/public_api.py` (≈ строки 188, 1491). Сейчас неизвестный слаг
отдаёт «любую страну с именем ~uzbek» — в мультиаренде это выдача чужих данных.
Заменить на явный 404/ошибку. Добавить тест: неизвестный слаг → не отдаёт
чужого арендатора.

### 3.4 — Защита «в глубину»: централизованный скоуп
Добавить helper/менеджер, который гарантирует `tenant_id` в запросах
(defense-in-depth), **не убирая** существующие ручные `.filter(country=...)`.
Обязательно: выставлять арендатора в cron-командах
(`foodcost/management/commands/*`), иначе фоновые задачи получат пустые выборки.

### 3.5 — Роли вместо `is_superuser`
~17 мест (в основном `foodcost/views.py`, `foodcost/order_views.py`). «Админ
клиента» не должен быть Django-суперюзером. После этого — перевернуть
`test_django_superuser_bypass_is_documented` в ловушке на новое поведение.

### 3.6 — Онбординг/провижининг (позже)
Самостоятельная регистрация арендатора + автосоздание кабинета (арендатор +
первый филиал + админ + дефолтные справочники).
